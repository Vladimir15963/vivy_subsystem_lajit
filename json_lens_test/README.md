# JSON Lens —— 给 Godot 编辑器用的超长 JSON 阅读器（可压缩、可编辑）

一个编辑器插件（主屏工具，和 2D / 3D / Script 并列的标签页）。
为「几 MB ~ 几十 MB、几十万个节点的 JSON」设计：**异步解析、虚拟化滚动、行内合并、重复收缩、可编辑保存**。

不需要改你现有项目——这个文件夹本身就是一个干净的 Godot 4.7 测试工程。

> **你要读的是 `dsh_text.json` 这类「卡片 / 对话快照」？**
> 打开后会自动识别格式并切到「卡片视图」（见第十节），2776 张卡、36 万个节点，
> 折叠时只有 2776 行、构建耗时 54 ms。

---

## 一、怎么跑起来

1. 用 Godot 4.7 打开 `json_lens_test` 这个文件夹（`project.godot` 在这里）。
2. 插件已在 `project.godot` 的 `[editor_plugins]` 里启用，编辑器扫描完资源后，顶部标签栏会多出 **JSON Lens**。
3. 点它 → 工具栏「打开 JSON…」→ 选 `sample/demo.json`（1.6 MB / 28,804 节点 / 800 个玩家存档）。
   也可以把 `.json` 文件直接拖进面板。

> 标签页没出现的话：`项目 → 项目设置 → 插件`，确认 `JSON Lens` 是启用状态，重启编辑器。

打开后会记住上次读的文件（`user://json_lens.cfg`）。

## 二、压缩显示：这是这个工具的核心

普通 JSON 阅读器是「一个键一行」，几十万节点要翻几千屏。这里做两层压缩，目标是**一屏装下尽可能多的信息**，同时还能点开追细节。

### 1. 行内合并（INLINE）

一棵子树如果**全是标量**且压成一行不超过 130 字符，就整段摊在同一行上：

```
▸ 0: { id: 0, name: "玩家_0", level: 1, exp: 0, gold: 0, active: false, tags: ["新手村", "段位_1"] }
```

它仍然只占 1 行，但你不用再展开就能读到全部内容。含子容器的节点不会被合并（否则会失去层次）。

### 2. 重复收缩（GROUP）

数组里**连续一段同构的元素**收成一行，并标出覆盖的区间和数量：

```
▸ [0..799]  ×800  {id, name, level, exp, gold, active, tags, last_battle, bag, note}
```

「同构」用**形状签名**判断：只看类型 / 键名 / 子结构，不看标量值 ——
所以 800 条 id 各不相同的记录照样能收成一行。点箭头（或回车）就地展开成逐行。

标量数组只在**值完全重复**时才收（例如一整个 `[null, null, …]`），避免把有差异的数据藏起来。

### 3. 根节点不参与行内合并

否则一份小 JSON 会整份变成一行，反而没法导航。所以顶层结构始终是一行一个键。

### 效果（实测）

| 文件 | 节点数 | 不压缩 | 行内合并 | 行内 + 重复收缩 |
|---|---|---|---|---|
| 3000 条同构记录 | 24,004 | 18,004 行* | 18,004 行 | **4 行** |
| `sample/demo.json` | 28,804 | 十几万行 | 数百行 | **约 5 行** |

\* 展开到第 3 层时的可见行数。工具栏「压缩」下拉可以随时在三种模式间切换：
`不压缩 / 行内合并 / 行内 + 重复收缩`（默认最后一种）。

两种压缩都只是**显示层**的规则，不改动数据；展开/折叠是纯视图状态，撤销走的是编辑栈，互不干扰。

## 三、编辑

选中一个**标量**节点，详情栏会出现编辑行：`[类型▾] [值] [应用] [删除]`。

- **类型▾**：字符串 / 数字 / 布尔 / null，可以互转。
- **值**：按所选类型校验（数字必须真能转 float、布尔只接受 `true`/`false`），不合法会在状态栏提示而不写入。
- **应用**：写入模型、标记「● 未保存」。
- **删除**：把节点从父节点上摘掉（不是删数组元素，是删这个键/元素）。根节点不可删。
- **撤销**：撤销改值 / 改类型 / 改键名 / 删除，可连续撤销（最多 300 步）。
- **保存**：Ctrl+S 等价按钮，把整棵树按 2 空格缩进美化后写回原文件。

改值后 `flat_len` / 形状签名会沿祖先链重算，所以压缩显示、`$.a.b` 路径、序列化结果立刻同步。

**未保存保护**：有未保存修改时标题会变成 `● 文件名`，此时打开别的文件或点 ↻ 重载会弹确认框（丢弃 / 取消）。

> 注意：保存会把文件重写成 2 空格缩进的格式化形式（原文件的紧凑写法和空白不会保留）。

## 五、为什么它能扛住超长 JSON

**1. 摊平成类型化数组，而不是建树**

`JSON.parse()` 出来的 `Variant` 树本身没问题，问题是不能把它变成几十万个 `TreeItem`（每个都是 `Object`，分配 + GC 直接把编辑器拖死）。

`json_lens_model.gd` 一次前序遍历把整棵树摊进 9 个 `Packed*` 数组
（`kinds / keys / texts / parents / first_child / next_sibling / index_in_parent / counts / depths`），
每节点约 25 字节 + 键值文本，没有任何 `Object` 分配；摊平后原来的 `Variant` 树立刻丢掉。

前序摊平还带来两个红利：
- 一个节点的全部子孙 id 是**连续区间** → 折叠 = 跳下标，行号 ↔ 节点 O(1)；
- 子节点 id 恒大于父节点 → **倒着扫一遍就能自底向上**算完压缩元数据。

压缩用的两份元数据也是数组：
- `flat_len[id]`：这棵子树压成一行要多少字符（-1 = 含子容器，压不了）
- `sig[id]`：形状签名（乘法滚动哈希：类型 + 键名 + 子签名）

**2. 虚拟化渲染**

`json_lens_rows.gd` 不是 `Tree`，是自绘 `Control`：控件高度 = 可见行数 × 行高（可能几千万像素），
`_draw()` 只画滚动位置命中的那 40 来行。每行几次 `draw_string`，没有节点对象、没有布局计算。

行数据是三个平行数组：`rows`（首节点 id）/ `row_start`（组起始下标）/ `row_len`（组长度=1 表示普通行）。
展开状态用「隐式默认深度 + 显式覆盖表」表示，「折叠全部 / 展开到 N 层」改一个整数就完事（0 ms）。

**3. 解析在后台线程，UI 永不冻结**

`json_lens_worker.gd` 把「读文件 + 解析 + 摊平」丢进 `WorkerThreadPool`，主线程每帧非阻塞轮询，
状态栏显示「解析中… 已构建 N 个节点」。

线程安全约定（有实测依据，别随手改）：
- `Model` 在工作线程里 new + 写满，再通过 `Mutex` 一次性交给主线程，之后主线程独占读取——任何时刻只有一个线程碰它。
- **绝不让工作线程去读主线程持有的 GDScript 对象（哪怕只读）**。Godot 4.7 上这会让进程在退出时崩掉（`0xC0000005`）。
  所以**搜索没有放进 WorkerThreadPool**，而是主线程每帧扫 24,000 个节点的分帧扫描——同样不卡 UI，还天然可取消、可显示进度。
- 取消用「代号（generation）」：每次 `start_load` 让 `_gen` 自增，旧任务的回写因代号不匹配被丢弃。

### 实测数据（Godot 4.7.2，`tests/json_lens_test.gd`）

| 项目 | 结果 |
|---|---|
| 6.5 MB / 600,004 节点 | 解析 2.3 s（其中纯 `JSON.parse` 占 0.55 s） |
| 600,004 节点全部展开成可见行 | 1.2 s（一次性操作），折回 2 层 0 ms |
| 展开 / 折叠单个节点 | 只重算可见行，毫秒级 |
| 单行渲染 | 永远只有约一屏 |
| 改一个值 | 立即，仅沿祖先链重算压缩元数据 |
| 保存（6.5 MB 级） | 序列化 + 落盘约 1~2 s（期间状态栏提示「保存中…」） |

## 六、已知限制

- **数字精度**：`JSON.parse()` 把数字统一读成 `float`，超过 2^53 的整数（雪花 ID 之类）会失真。整数会显示成 `1` 而不是 `1.0`，但 `12345678901234567890` 这种原始写法无法保留。
- **键序**：显示顺序 = 解析后的字典顺序。注意 `JSON.stringify()` 会按键名排序输出，所以 `sample/demo.json` 里的字段是字典序的——不是阅读器排的序。
- **保存会重写格式**：统一成 2 空格缩进，不保留原文件的紧凑写法 / 注释（JSON 本来也没有注释）。
- **编辑范围**：可以改标量值、改类型、改键名、删节点；**不支持新增节点**，也不支持直接改容器结构。
- **搜索范围**：只搜键名和字符串值（不搜数字字面量），最多 50,000 条。
- **行内预算**：130 字符（`json_lens_rows.gd` 的 `INLINE_BUDGET`），想放宽可以调大。
- 单文件单标签，没有「多标签」。

## 十、格式适配：`dsh_text.json` 这类文件

### 它长什么样

```json
{ "n0": 120,
  "changes": [
     [120, "", ["", "", ""], []],
     [126, "avatars/a1_seed.png", ["", "", ""],
       [["composer", "描述你想要构建的内容，/ 调用指令，@ 文件或对话"],
        ["model", "选择模型"],
        ["ai", "我"], ["ai", "在"], ["ai", "。"], ["ai", "我在。"],
        ["meta", "用时 0.4秒"]]]
  ]}
```

- 单行 JSON，2.78 MB，**363,545 个节点**
- `changes` 下有 **2776 张卡**，每张卡是 `[id, 头像, [3 个颜色], 事件列表]`
- 事件列表有 **113,778 条** `[kind, text]`，kind 共 13 种：
  `ai`(43138) · `meta`(18516) · `pill`(10248) · `user`(10107) · `card`(8162) ·
  `sub`(7987) · `model`(3711) · `dot`/`name`/`state`(各 2601) · `composer`(2136) · `err`(1651) · `code`(319)
- 大量文本被切成了**单字碎片**：`["ai","我"] ["ai","在"] ["ai","。"]`
- 最长文本 1783 字符

拿通用结构视图读它，屏幕上全是 `["ai", "我"]` 这种数组，人得自己拼句子。

### 卡片视图做了什么

打开这个文件后，`json_lens_schema.gd` 认出「条目集合 → 条目 → `[kind, text]` 事件列表」这个形状
（只看结构、不写死字段名），工具栏出现「视图」切换并**默认切到卡片视图**：

```
▸ #120   1 条                                                      ← 卡片头
▸ #126  avatars/a1_seed.png  [3]  12 条  描述你想要构建的… 选择模型…
▾ #178  avatars/a1_params00.png  [3]  8 条
    composer  描述你想要构建的内容，/ 调用指令，@ 文件或对话        ← 事件行
    model     选择模型
    user      你好
    ai        我在。我在。                                          ← 3 个碎片合并成一句
    ai        这是一整句完整的话。
    meta      用时 0.4秒
```

四件事：

1. **命名行**：卡片第 0/1/2 位显示成 `#id`、头像、`[颜色数]`，不再是裸数组
2. **碎片合并**：连续同 kind、且都很短（≤ 6 字符）的片段拼成一句显示；
   `["ai","我"] ["ai","在"] ["ai","。"]` → 一行 `ai  我在。`（行上记着 span，
   选中时仍精确定位到**第一个**片段的文本节点，方便单独编辑）
3. **软换行**：长文本按可用宽度自动折行（最多 8 个视觉行），1783 字的行也能读
4. **按 kind 着色**：`ai` 正文色、`user` 蓝、`card`/`name` 黄、`meta`/`pill` 灰、`err` 红、`code` 绿

### 读 / 改的工作流

- 卡片默认**全部折叠**，2776 行一目了然，卡片头带正文摘要
- 点箭头（或回车 / 双击）展开单张卡；「层级 ▾」里选 **全部展开** 就是通读模式
- 点任意事件行 → 详情栏出现 `[类型▾][值][应用][删除]`，**改完点应用即可**
- 想改整块结构 → 切到「结构视图」，在树里精确增删（两个视图共享同一个选中节点）
- 搜索照旧：命中后双击结果，卡片视图会自动展开对应卡片并定位到那一行
  （例：搜 `调用指令` 会直接跳到 `$.changes[1][3][0][1]`）

### 这个格式下实测

| 项目 | 结果 |
|---|---|
| 解析 2.78 MB / 363,545 节点 | 1.0 s（后台线程） |
| 折叠视图 | **2776 行**（= 卡片数），构建 **54 ms** |
| 展开单张卡 | 毫秒级，只重算这一张卡的行 |
| 结构视图（行内+重复收缩） | 504 行 |

### 想适配别的格式

`json_lens_schema.gd` 的 `detect()` 只用结构做判断，返回一个 profile
（`entries` / `events_index` / `count`）。同形态的 JSON 会自动套用；
形状不同的话，改 `detect()` 的判定规则即可，卡片视图本身不需要动。
`json_lens_cards.gd` 顶部的 `SHORT_FRAG`（碎片阈值）、`MAX_VIS_LINES`（软换行上限）、
`KIND_W`（kind 列宽）都是可以按口味调的常量。

## 十一、修复记录

### 反复折叠导致的尺寸漂移（已修）

三处都是「尺寸只增不减 / 量错了基准」导致的，症状是反复点折叠箭头后视图越来越宽、右边多出大片空白，或每行右侧被裁掉十几个像素：

| 位置 | 原因 | 修法 |
|---|---|---|
| 结构视图内容宽度 | `_content_w` 只在换文件时重置，绘制里**只增不减**；逐层展开后 `x + w` 越来越大，折叠回来也不回收，最终涨到 `MAX_CONTENT_W`(24000 px) | 每次 `rebuild()` 按当前可见行重新测宽，基准取「视口宽」 |
| 结构视图视口宽 | `_view_w()` 用的是 `scroll.size.x`（外框宽，含垂直滚动条），内容恒比视口宽十几像素 → 横向滚动条常驻 | 扣掉垂直滚动条宽度 |
| 卡片视图宽度 | `custom_minimum_size.x = 视口宽 - 2`，但滚动容器还要扣滚动条 → 子控件比视口宽、每行右端被裁 | 宽度完全交给 `ScrollContainer`（横向滚动禁用时子控件铺满视口），自身只用 `size.x` 算换行宽 |

回归测试（`tests/json_lens_test.gd` 的「反复折叠/展开不应让尺寸漂移」）会连续折叠展开 8 次，
断言宽高**精确**回到基准值；卡片视图也有对应一组。这两组断言在修之前是失败的。
### 「重复收缩」的组行展开后收不回去（已修）

症状：点 `[0..799] ×800` 那个组行能展开，但展开之后**再也收不回去**——
组行从视图里消失了，箭头变成了「第一个成员自己的箭头」，点它只会展开那个成员，
而且每点一次还会多出两行。

原因有两个：

1. 展开后组行不再出现在 `rows` 里，用户没有可以点的「收起点」；
2. 分组判定里带了 `not _expanded_members.has(cid)`，所以一旦展开，连组头都不会再生成，
   成员直接变成散行。

修法：**组头行永久保留**，展开时成员行接在组头下面（组头箭头朝下），点组头即可收回；
分组判定不再看展开状态，展开只决定「要不要在组头后面接成员行」。
顺带补了 `grab_focus()` 的 `is_inside_tree()` 保护（无头测试里控件还没进树时会报错）。

### 卡片视图「选不了节点」（可点范围太小，已改善）

现象：卡片视图里点来点去只能点到整张卡，选不到里面的对话文本。

其实选中逻辑本身是通的（面板级点击测试可以验证：点卡片头 → `_sel_id` 变成这张卡，
点事件行 → 选中 `$.changes[1][3][0][1]` 这样的文本节点并出现可编辑行）。
问题是**可点范围太小**：

- 卡片默认全部折叠，整屏只有卡片头能点；
- 点卡片头选中的是「整张卡」这个**容器**，详情栏的编辑行是隐藏的（容器没有可编辑的标量值）。

于是看起来就像「点了没反应 / 选不了东西」。改了三处：

| 行为 | 现在 |
|---|---|
| 单击卡片头 | 选中这张卡，**并且顺手展开它**，立刻能看到里面的事件行 |
| 单击事件行的文本 | 选中该文本节点，详情栏变成可编辑 |
| 单击事件行的 kind 标签（`ai` / `user` / `meta`…） | 选中 kind 这个字符串节点，也能改 |
| 双击事件行 | 选中并直接跳到详情栏编辑框（和结构视图一致） |
| 单击箭头（左侧 30px） | 只做展开/收起 |

测试：`tests/json_lens_ui_test.gd` 末尾用真实的 `InputEventMouseButton`
在卡片视图里依次点卡片头 / 事件文本 / kind 标签，断言 `_sel_id` 与可编辑状态都对。
### 卡片视图「点行完全没反应」（已修）—— 控件宽度是 0

这条最隐蔽。诊断输出（`tests/json_lens_dispatch_test.gd`）：

```
cards.size = (0.0, 58296.0)      ← 宽度 0 ！！
cards_scroll.size = (1061.0, 200.0)
```

控件矩形宽度为 0 → `Control.has_point()` 永远为假 → Godot 的 GUI 拾取永远选不到这个控件
→ 事件根本不派发进来 → 不高亮、详情栏一直是「未选中节点」。

而**画面看起来是正常的**：绘制时 `_view_w()` 有「拿不到自身宽度就用滚动容器宽」的兜底，
所以文字照样按正确宽度折行，只是控件本身没有可点区域。

根因：上一轮修「宽度溢出」时把 `custom_minimum_size.x` 设成 0，以为 ScrollContainer 会把
子控件铺满视口。实际上**Godot 的 ScrollContainer 只在子控件带 `SIZE_EXPAND` 时才铺满**，
否则子控件宽度就等于 `custom_minimum_size`（= 0）。

修法：

1. 两个视图都加 `size_flags_horizontal = Control.SIZE_EXPAND_FILL`；
   宽度变成 `MAX(视口宽, 内容最小宽)`，内容窄时铺满、内容宽时才出横向滚动条。
2. 卡片视图的换行宽度改按「滚动容器宽 − 垂直滚动条宽」计算
   （控件自身 `size.x` 含滚动条那一条，会让每行右端被盖住）。

**教训**：前两个测试文件都是直接调 `_gui_input()`，绕过了控件拾取、坐标变换和裁剪，
所以「控件不可点」这类问题它们抓不到。新增的 `tests/json_lens_dispatch_test.gd`
用 `Viewport.push_input()` 走完整链路：建窗口 → 建面板 → 打开真实文件 →
在窗口坐标上点行 → 断言真的选中；并且专门验证**结构视图最右侧**也能点中
（内容窄时控件不铺满，右侧那一片以前是点不到的）。
